# Mindeck: Stand aller vier Repos und Weg zum Launch (2026-10-29)

Geprüft wurden `mindeck` (develop), `mindeck-cloud` (develop), `mindeck-mobile` (develop) und
`mindeck-web` (feature/website-redesign), jeweils auf Sicherheit, offene Arbeit und Launch-Reife.
Alles hier Behobene ist am 2026-10-31 auf diesen Branches committet (noch nicht gepusht).

## 1. Kurzfazit

Das Produkt ist weiter, als die Dokumentation sagt: Onboarding, Import aus VS Code und Browsern,
rund 20 Sprachserver, SCM mit PRs, Auto-Update und eine komplette Release-Pipeline sind da. Zu
kaufen ist es trotzdem noch nicht. Es fehlt kein großes Feature, aber fünf Dinge um den Code herum:

1. **Mindeck Cloud ist nirgends gehostet.** Eine installierte App braucht sie schon für den Test.
2. **Es gab noch nie einen Release.** Keine Tags, keine Secrets, keine Signatur. Alle Download-Links der Website sind 404.
3. **Die Rechtstexte sind Entwurf.** Impressum-Platzhalter, AGB versprechen mehr als der Code, Datenschutz unvollständig.
4. **Die Handy-App koppelt auf echten iPhones nicht** (M1) und hatte einen Klartext-Fallback. Beides ist jetzt behoben, braucht aber einen neuen nativen Build.
5. **Die CI war rot** (Coverage 99,95 % statt 100 %, jetzt behoben), und die Audits von Mobile und Web lagen nie auf `develop`.

## 4. Plan bis zum Launch

Jede Phase ist für eine eigene Claude-Code-Runde geschnitten. „Fertig“ heißt: Tests grün, im
Repo dokumentiert, von Robin committet.

### Phase A: Pushen und CI grün (1 Tag)
- Die Commits dieses Berichts pushen und die CI abwarten.
- mindeck: Branch-Schutz für `main`/`develop` mit Pflicht-Checks, E2E einmal lokal (`npm run test:e2e`, nach dem Electron-Update).
- mindeck-mobile: neuer nativer Build (`npm run ios`) und QR-Kopplung auf dem iPhone testen (M1).
- Die Audit-Pläne von Mobile und Web liegen nur auf `origin/feature/claude-remote`; als `AUDIT-PLAN.md` nach `develop` holen und mit den Status-Tabellen aus §6 aktualisieren.
- **Fertig:** CI auf allen vier Repos grün, iPhone koppelt per QR.

### Phase B: Cloud live (2–3 Tage, nach E1)
- `fly.toml` oder Compose auf dem neuen Server, Postgres in Frankfurt mit `sslmode=verify-full`, `keys:generate` (alle drei Schlüssel offline sichern), Migrationen, `admin:create` + 2FA.
- SMTP bei einem EU-Anbieter mit AVV, SPF/DKIM/DMARC für mindeck.de.
- Stripe live: Preis, AGB-URL im Dashboard (sonst scheitert der Checkout), Webhook mit den sechs Events aus dem Cloud-README, ein echter Testkauf mit Erstattung.
- Backups mit age-Empfänger und Offsite-Ziel, ein Restore-Test. Uptime-Check auf `/health`, Alarme für 5xx und Mailfehler.
- Website deployen (`PUBLIC_SITE_URL`, `PUBLIC_API_URL`). Die neue Build-Sperre verlangt vorher die Impressum-Daten (E6).
- **Fertig:** Registrieren → Mail → Test → Kauf → Lifetime funktioniert von außen.

### Phase C: Erster Release (1–2 Tage, nach E3/E4)
- GitHub: Variable `MINDECK_CLOUD_URL`, Secrets `MINDECK_CLOUD_KEY`, `CSC_*`, `APPLE_*` (docs/RELEASE.md).
- `develop` per PR nach `main`, Workflow einmal manuell, dann Tag `v1.0.0`.
- Installer auf einem frischen Mac und einem frischen Windows-PC testen (BE-SEC-03 steht dort noch auf „zu prüfen“).
- **Fertig:** Download-Buttons der Website liefern signierte Installer, Auto-Update greift.

### Phase D: Recht und Vertrauen in der App (2 Tage)
- Desktop: AGB/Datenschutz-Links und Zustimmung bei der Registrierung (`CloudForms.tsx`), „Über“ mit Impressum, Datenschutz, Lizenzen, Support-Mail; `THIRD_PARTY_NOTICES` beim Build erzeugen.
- „Problem melden“ mit „Diagnose kopieren“, Crash-Upload als Opt-in.
- Checkout: Widerrufsverzicht als eigene Checkbox mit Link auf `/withdrawal`, AGB und Widerrufsbelehrung in der Bestätigungsmail (§312f BGB).
- Datenschutzerklärung ergänzen: Trial-Ledger, `metadata.user_id`, `ai_usage` 12 Monate pseudonymisiert, Kamera/Fotos/lokales Netz (Handy), GitHub (Downloads und Auto-Update), Cookie-Laufzeit.
- **Fertig:** Anwalt hat AGB, Widerruf, Datenschutz und Checkout gesehen.

### Phase E: Handy store-fertig (3–5 Tage)
- EAS: `eas init`, `development`-Profil, Submit-Konfiguration, APNs-Schlüssel.
- App-Review-Zugang (M5): Demo-Konto und ein dauerhaft erreichbarer Demo-Core mit mehrfach nutzbarem Review-Code.
- Offene Sicherheitspunkte: Keychain `THIS_DEVICE_ONLY` mit Migration (MOB-SEC-05), `+native-intent`-Allowlist ohne `prompt`-Parameter (MOB-SEC-10), Host-Bestätigung nach dem Scan und kein Cloud-Passwort an den Core (MOB-SEC-08), Terminal-/Editor-Webviews auf ihr Bundle festlegen.
- Android: `choose()` zeigt maximal drei Optionen. Files verliert dadurch fünf von acht Aktionen (MOB-BUG-01); eigenes Action-Sheet.
- **Fertig:** TestFlight intern, Android-APK, beide koppeln per QR.

### Phase F: „Glücklich in der ersten Woche“ (laufend)
Nach Wirkung für zahlende Nutzer sortiert:
1. **Test-Ende ankündigen:** Chip in der Kopfleiste bei 60 und 15 Minuten Rest, mit Kaufen-Knopf. Bisher sperrt ein Overlay mitten in der Arbeit.
2. **Browser behält Tabs:** Einstellung „Dort weitermachen, wo ich aufgehört habe“, angeheftete Tabs bleiben. Heute startet jeder Start leer (059e6ea).
3. **Sprachserver für Vue, Svelte, Astro, Tailwind, Prisma:** Die Kernzielgruppe (Next/Vite/Tailwind) stößt am ersten Tag darauf.
4. **Handy, Adresse ändern:** mehrere Adressen pro Core (LAN, Tailscale) und Diagnose statt nur „nicht erreichbar“. Die Website verspricht VPN-Zugriff.
5. **Onboarding:** git-Prüfung, Homebrew-Prüfung, Schritt „Handy koppeln“ (der Haken des Produkts), geführter erster Agent-Lauf.
6. FE-BUG-12 (Outline leer bei manchen TS-Dateien).
7. README für Käufer neu schreiben. Es nennt Mobile, Installer und Auto-Update als „nicht gebaut“ und beschreibt das entfernte Command Deck.

### Phase G: Mindeck Anywhere
Nach dem Launch, wie in `docs/ANYWHERE_PLAN.md` (Relay zuerst). Erst damit funktioniert das
Handy auch außerhalb des WLANs. Für den Verkauf ist das der größte Hebel.
